# 二、本阶段核心目标

M7.3 解决：

```
Agent
  ↓
当前对话
  ↓
当前 Session
  ↓
历史 Agent Context
```

```
Conversation Memory
Run Context Memory
User Preference Memory
```

# 三、先明确 Memory 是什么

本项目中：

```
Skill
=
知识 + 方法 + 操作指导

MCP
=
可执行能力 + Resource

Memory
=
过去发生过什么，以及当前 Agent 应该记住什么
```

例如：

### Skill

```
WNS < 0 表示存在 timing violation
```

这是稳定知识。

### MCP

```
get_run(run_id)
```

这是实时能力。

### Memory

```
用户刚才分析了：
run 20261008-xxx

该 Run 的 STA WNS = -0.42ns

用户要求继续分析 setup violation
```

这是历史上下文。

# 四、Memory 不等于 RAG

这是本阶段最重要的边界。

不要把：

```
Memory
```

实现成：

```
Vector Database
+
Embedding
+
RAG
```

本阶段禁止：

```
❌ Chroma
❌ Milvus
❌ FAISS
❌ Elasticsearch
❌ Embedding
❌ Vector Search
❌ Reranker
❌ GraphRAG
```

因为：

```
Memory
```

解决：

> “我之前和你做过什么？”

而：

```
RAG
```

解决：

> “知识库里有什么？”

两者不是同一个问题。

# 五、Memory 分层

本阶段实现三层：

```
L1 Short-Term Memory
        ↓
L2 Session Memory
        ↓
L3 Long-Term Memory
```

但是三层的实现复杂度不同。

# 六、L1 Short-Term Memory

L1 是当前 Agent 调用中的：

```
messages
```

例如：

```
User:
分析 run xxx

Assistant:
我先获取 Run 信息。

Tool:
...

Assistant:
WNS = -0.42ns
```

这些已经存在于 LangGraph：

```
AgentState.messages
```

因此：

> 不要重复实现第二套 messages storage。

M7.3 必须明确：

```
LangGraph State
=
Short-Term Working Memory
```

# 七、L2 Session Memory

解决：

```
同一个 session_id
```

多个请求之间保持上下文。

例如：

### 第一次

```
User:
帮我分析 run A
```

Agent：

```
WNS = -0.42ns
```

### 第二次

```
User:
为什么会这样？
```

Agent 应该理解：

```
“这样”
=
run A 的 timing failure
```

而不是重新问：

```
哪个 Run？
```

# 八、LangGraph Checkpointer

优先复用现有：

```
LangGraph
+
Checkpointer
```

不要重新实现：

```
message_history table
```

如果 M6.6 当前已经使用：

```
MemorySaver
```

必须分析它的实际生命周期。

尤其确认：

```
Agent process restart
```

之后 Memory 是否还存在。

如果：

```
MemorySaver
```

只是进程内存：

必须在文档中明确：

> 当前属于 process-local session memory。

# 九、M7.3 第一阶段不引入数据库

本阶段默认：

```
MemorySaver
```

或者 LangGraph 当前官方推荐的轻量 Checkpointer。

不要直接加入：

```
PostgreSQL
Redis
MongoDB
```

除非现有代码已经存在明确基础设施。

原因：

M7.3 的目标是验证：

```
Session Memory architecture
```

而不是搭建生产级 Memory DB。

# 十、Thread 与 Session

必须明确：

```
session_id
```

与：

```
thread_id
```

的关系。

推荐：

```
session_id
    ↓
thread_id
```

即：

```
同一个 session_id
=
同一个 LangGraph thread
```

例如：

```
session_id = abc123
```

转换为：

```
thread_id = abc123
```

但不要让：

```
user message
```

直接任意控制：

```
checkpoint namespace
```

必须经过统一的 ID validation。

# 十一、M6.6 HITL 必须兼容

这是硬性要求。

之前：

```
LangGraph
 ↓
interrupt()
 ↓
checkpoint
 ↓
approval
 ↓
resume()
```

现在加入 Memory 后必须仍然成立。

例如：

```
User
 ↓
run_flow
 ↓
Policy
 ↓
interrupt
 ↓
checkpoint
```

之后：

```
approve
 ↓
resume(thread_id)
 ↓
original ToolCall
 ↓
MCP
 ↓
Platform
```

不能因为 Memory 改造破坏：

```
approval
thread binding
resume
exact-once execution
```

# 十二、M7.3 Memory API

设计一个清晰的 Memory abstraction。

例如：

```
MemoryStore
```

至少考虑：

```
get_session(session_id)
save_session(...)
append_event(...)
get_recent_context(...)
```

但：

> 不要过度设计。

不要现在实现：

```
50 个 Memory interface
```

# 十三、推荐 Memory 数据模型

建议至少区分：

```
Session
MemoryEvent
MemorySummary
```

例如：

```
Session
├── session_id
├── thread_id
├── created_at
├── updated_at
└── status
```

MemoryEvent：

```
MemoryEvent
├── event_id
├── session_id
├── type
├── timestamp
├── payload
└── metadata
```

可能的 event：

```
user_message
assistant_message
tool_call
tool_result
approval
run_reference
qa_result
```

但是：

> 不要把所有原始 ToolResult 无限复制进 Memory。

# 十四、Memory 与完整 Trace 的边界

这是一个重要设计点：

```
Trace
=
完整执行证据

Memory
=
未来 Agent 真正需要的上下文
```

例如：

```
完整 Docker log 100KB
```

应该：

```
Trace / Artifact
```

而不是：

```
Memory
```

Memory 可以保存：

```
{
  "run_id": "xxx",
  "operation": "rtl_to_sta",
  "wns_ns": -0.42,
  "tns_ns": -1.7,
  "engineering_status": "failed"
}
```

而不是保存：

```
全部 timing.rpt
```

# 十五、Memory Event

建议设计：

```
MemoryEvent
```

使用明确类型。

例如：

```
USER_MESSAGE
ASSISTANT_MESSAGE
RUN_REFERENCE
QA_RESULT
APPROVAL_EVENT
```

Tool call/result 是否直接进入长期 Memory：

> 默认不要。

它们属于：

```
LangGraph state / execution trace
```

只有经过 Memory Policy 提炼后，才可以进入 Session Memory。

# 十六、Memory Policy

必须增加：

```
MemoryPolicy
```

用于决定：

```
什么值得记
什么不应该记
```

例如：

### 可以记

```
run_id
flow name
timing result
QA result
用户明确要求记住的偏好
```

### 不应该记

```
API Key
Authorization
环境变量 secret
完整 prompt
完整 Docker logs
任意 filesystem path
完整 MCP response
```

尤其：

```
Secret
```

绝对不能进入 Memory。

# 十七、用户明确要求“记住”

必须支持一种显式机制：

```
User:
记住我后面分析 STA 都优先看 WNS。
```

这种情况下：

```
Memory
```

可以保存一个：

```
preference
```

例如：

```
{
  "type": "preference",
  "key": "timing.primary_metric",
  "value": "sta.wns_ns"
}
```

但不要自动把所有用户聊天内容都当成长期记忆。

# 十八、Preference Memory

可以设计：

```
PreferenceMemory
```

例如：

```
timing.primary_metric = sta.wns_ns
```

或者：

```
response.style = concise
```

但必须避免：

```
自动推断敏感个人信息
```

只保存：

```
明确表达
+
对 Agent 长期有用
```

的信息。

# 十九、Run Context Memory

这是本项目非常重要的一类 Memory。

例如：

```
用户正在分析 Run A
```

Memory 可以保存：

```
{
  "run_id": "20261008T...",
  "flow": "rtl_to_sta",
  "wns_ns": -0.42,
  "tns_ns": -1.7,
  "status": "failed"
}
```

这样用户下一轮：

```
继续分析
```

Agent 可以理解：

```
继续分析刚才的 Run
```

但必须注意：

> Memory 中的 Run 数据只是历史上下文，不是真实 source of truth。

# 二十、Source of Truth

必须建立优先级：

```
当前 Platform API
        ↑
Run / Artifact / QA
        ↑
Memory
```

即：

```
Memory
=
context hint

Platform
=
current truth
```

例如 Memory：

```
WNS = -0.42
```

但用户重新请求：

```
get_run
```

返回：

```
WNS = -0.31
```

应该使用：

```
current Platform result
```

而不是旧 Memory。

# 二十一、Memory Retrieval

M7.3 不使用 Vector Search。

可以采用：

```
session_id
+
recent events
+
explicit run_id
+
latest summary
```

例如：

```
User message
     ↓
SessionMemory
     ↓
Recent Context
     ↓
Relevant Run References
     ↓
LLM
```

# 二十二、Context Window 控制

Memory 最大问题之一：

```
越聊越长
```

所以必须增加：

```
MAX_MEMORY_CONTEXT_BYTES
```

或 token approximation。

例如：

```
32 KiB
```

具体值根据当前模型接口调整。

必须：

```
bounded
```

不能：

```
无限拼接历史消息
```

# 二十三、Memory Summary

当 Session 太长时，可以进行：

```
Recent Messages
        ↓
Summary
```

但是：

> M7.3 第一版不要引入第二个 LLM。

可以先采用：

```
deterministic summary
```

或者：

```
保留最近 N 条消息
+
结构化 Run Context
```

不要为了 Summary 再创建：

```
Summary Agent
```

也不要增加：

```
Multi-Agent
```

# 二十四、推荐 Context 结构

最终给 LLM 的 Memory Context 可以类似：

```
<memory>
Current Session:

Recent context:
- User asked to analyze run A.
- STA WNS = -0.42ns.
- QA result = FAIL.

Active run:
- run_id = A
- flow = rtl_to_sta

User preferences:
- Prefer WNS-first timing analysis.

Important:
Memory is historical context only.
Current Platform results are authoritative.
</memory>
```

必须与：

```
Skill Context
```

明确分离。

最终：

```
System Prompt
+
Skill Context
+
Memory Context
+
Conversation Messages
```

# 二十五、Memory 与 Skill 的关系

正确：

```
Skill
=
稳定的方法论

Memory
=
当前用户/Session 的历史上下文
```

例如：

```
timing-analysis Skill:
WNS < 0 = timing violation
```

Memory：

```
这个用户正在分析 Run A
Run A 当前 WNS = -0.42
```

不能把：

```
Memory
```

写进：

```
SKILL.md
```

也不能让：

```
Skill Loader
```

负责 Memory。

# 二十六、Memory 与 MCP 的关系

MCP：

```
get_run(run_id)
```

获取实时信息。

Memory：

```
上一次用户分析过 run A
```

因此：

```
Memory → 提供上下文
MCP → 获取最新事实
```

推荐流程：

```
Memory
 ↓
发现 active_run = A
 ↓
MCP get_run(A)
 ↓
获取最新结果
 ↓
覆盖旧 Context
 ↓
LLM
```

这也是本项目未来 Agent 可靠性的核心。

# 二十七、Memory 与 HITL

Memory 不得决定：

```
approve
reject
```

例如：

```
Memory:
用户以前批准过 run_flow
```

不能推导：

```
这次自动批准
```

必须：

```
每一次 HIGH RISK Tool Call
        ↓
PolicyEngine
        ↓
HITL
```

Memory 只能提供：

```
historical context
```

不能提供：

```
authorization
```

# 二十八、Memory Security

必须禁止 Memory 保存：

```
API Key
Authorization Header
Bearer Token
Cookie
Password
Secret
完整环境变量
```

同时避免保存：

```
完整 MCP response
完整 Docker logs
完整 system prompt
```

Memory 写入前进行：

```
MemoryPolicy
```

过滤。

# 二十九、Memory Storage

M7.3 默认使用：

```
LangGraph Checkpointer
+
轻量 Session Memory abstraction
```

如果当前 LangGraph 已有：

```
MemorySaver
```

优先复用。

可以额外增加：

```
InMemoryMemoryStore
```

保存结构化 Memory：

```
session
run references
preferences
summaries
```

但：

> 不要把 MemoryStore 重新实现成完整 Checkpointer。

二者职责不同：

```
Checkpointer
=
Graph execution state

MemoryStore
=
Agent semantic memory
```

# 三十、MemoryStore 与 Checkpointer

必须在代码和文档中明确：

```
Checkpointer
```

保存：

```
AgentState
tool call state
interrupt state
resume state
```

而：

```
MemoryStore
```

保存：

```
长期/跨请求语义上下文
```

不要混淆。

```

```

```

```

```

```
