# M6.2：Agent Backend 基座 + PlatformClient

## 0. 当前项目状态

当前项目已经完成：

- M0 工程基座
- M1 Run / Result Envelope / SQLite Index
- M2 ToolDriver / Docker / Yosys / OpenSTA
- M3 Flow Engine
- M4 Report Parser
- M5 QA Engine
- M6.0 三端 Contract
- M6.1 Platform HTTP Server

当前整体架构：

```
Frontend
    │
    │ Agent API Contract
    ▼
Agent Backend
    │
    │ Platform API Contract / HTTP
    ▼
Platform Backend
    │
    ▼
Deterministic Core
    │
    ▼
```

M6.1 已经完成：

```
Platform Backend
├── FastAPI HTTP Server
├── PlatformApi

```

Platform Backend 已通过：

```
contracts/platform-api.yaml
```

对外提供稳定 HTTP API。

# 1. M6.2 唯一目标

本阶段建立一个：

> **与 Platform Backend 完全独立的 Agent Backend。**

最终必须能够形成：

```
┌─────────────────────────────┐
│       Agent Backend         │
│                             │
│  FastAPI                    │
│      │                      │
│      ▼                      │
│  Agent Application         │
│      │                      │
│      ▼                      │
│  PlatformClient             │
└─────────────┬───────────────┘
              │ HTTP
              ▼
┌─────────────────────────────┐
│      Platform Backend       │
│                             │
│ FastAPI → PlatformApi       │
│          → Flow / Run / QA  │
└─────────────────────────────┘
```

# 2. 本阶段最重要的架构原则

## Agent Backend 不得 import Platform 内部代码

禁止：

```
from aemp.flow import ...
from aemp.qa import ...
from aemp.runs import ...
from aemp.drivers import ...
from aemp.api.services import PlatformApi
```

甚至不要通过：

```
from aemp import ...
```

间接访问 Platform Core。

Agent Backend 与 Platform Backend 必须是：

```
进程隔离
+
代码隔离
+
HTTP Contract 隔离
```

Agent Backend 唯一访问 Platform 的方式：

```
HTTP
 ↓
Platform API Contract
```

# 6. 为什么不放进 src/aemp/agent

不要把 M6.2 实现成：

```
src/aemp/agent/
```

当前阶段的目标就是验证：

```
Agent Backend
≠
Platform Backend
```

如果 Agent 代码直接存在：

```
src/aemp/
```

很容易重新形成：

```
Agent → aemp.flow
Agent → aemp.qa
Agent → aemp.runs
```

从而破坏三端隔离。

未来如果决定把 Agent 单独拆成 Git Repository，也应该基本不需要重构。

# 7. Contract 的来源

Agent Backend 需要消费：

```
contracts/platform-api.yaml
contracts/agent-api.yaml
```

但：

> Agent Backend 不允许复制一套与 Platform 不一致的 API 定义。

建议：

```
agent-backend/contracts/
```

只保存：

```
Contract version
Contract reference
```

或者通过项目结构共享：

```
../contracts/
```

具体方案根据当前仓库实际结构决定。

必须避免：

```
Platform Contract v1
Agent 自己复制一份 v1
后来两边逐渐不一致
```

# 8. PlatformClient

这是 M6.2 最核心的组件。

实现：

```
agent_backend/platform/client.py
```

职责：

> 将 Platform HTTP API 封装为 Agent Backend 可以使用的稳定客户端。

例如：

```
class PlatformClient:
    def run_flow(...):
        ...

    def list_runs(...):
        ...

    def get_run(...):
        ...

    def run_qa(...):
        ...

    def list_artifacts(...):
        ...

    def get_artifact(...):
        ...
```

# 9. PlatformClient 不允许做业务判断

例如：

```
def run_qa(...):
    response = ...
```

可以。

但禁止：

```
if wns < 0:
    return "timing failed"
```

也禁止：

```
if result["status"] == "FAIL":
    ...
```

除非只是 transport-level error handling。

原因：

```
QA 判断
    ↓
Platform Backend
    ↓
QAEngine
```

而不是：

```
Agent Backend
    ↓
重新实现 QA
```

# 10. HTTP Client

可以使用：

```
httpx
```

不需要：

```
requests
aiohttp
grpc
```

除非仓库已有明确技术约束。

M6.2 建议同时支持：

```
sync PlatformClient
```

暂时不要实现：

```
async PlatformClient
```

除非测试或现有架构确实需要。

# 11. Platform URL 配置

环境变量：

```
AEMP_PLATFORM_BASE_URL=http://127.0.0.1:8000
```

Agent Backend 不应该硬编码：

```
"http://127.0.0.1:8000"
```

配置模型：

```
AgentConfig
├── platform_base_url
├── request_timeout_s
└── log_level
```

默认 timeout 要合理。

不要无限等待。

# 12. PlatformClient Error

需要区分：

### HTTP 业务错误

例如：

```
404 RUN_NOT_FOUND
```

应该转换成：

```
PlatformApiError
```

并保留：

```
code
message
details
http_status
```

### 网络错误

例如：

```
connection refused
timeout
DNS error
```

转换成：

```
PlatformConnectionError
```

### 响应格式错误

例如：

```
HTTP 200
但 JSON 不符合 Contract
```

转换成：

```
PlatformContractError
```

不要把所有异常统一成：

```
RuntimeError
```

# 13. Transport Error 与业务 Error 必须分离

例如：

```
Platform Backend
      │
      ├── 404 RUN_NOT_FOUND
      │
      ├── 422 FLOW_VALIDATION_FAILED
      │
      └── 503 TOOL_ENVIRONMENT_UNAVAILABLE
```

这些是：

```
Platform Business/API Errors
```

而：

```
connection refused
timeout
invalid JSON
```

属于：

```
Agent ↔ Platform Transport Errors
```

两者必须可以区分。

# 14. Response Contract Validation

PlatformClient 不应该盲信 HTTP 200。

例如：

```
HTTP 200
↓
JSON
↓
Schema validation
↓
DTO
```

可以复用 JSON Schema / Pydantic。

但注意：

> 不要把整个 Platform Contract 重新复制成大量手写模型，除非确有必要。

优先考虑：

```
JSON Schema
+
轻量 DTO
```

或者项目已有 schema loader。

# 15. Chat API

M6.2 建立：

```
POST /api/v1/chat
```

但：

> **不接 LLM。**

它只是一个同步 Stub。

例如：

```
{
  "message": "帮我查看最近一次运行"
}
```

返回：

```
{
  "message": "Agent Backend is running, but LLM runtime is not enabled in M6.2.",
  "status": "stub"
}
```

必须严格遵守：

```
contracts/agent-api.yaml
```

如果当前 Contract 的字段不是上述结构，以当前 Contract 为准。

# 16. Agent API 与 Platform API 必须完全分离

Agent API：

```
POST /api/v1/chat
```

Platform API：

```
POST /api/v1/flows/run
GET  /api/v1/runs
GET  /api/v1/runs/{id}
POST /api/v1/runs/{id}/qa
...
```

Frontend：

```
只调用 Agent Backend
```

未来 Frontend 不应该：

```
Frontend → Platform Backend
```

除非未来经过明确架构调整。

# 17. Chat Application Service

建议：

```
agent_backend/application/chat.py
```

提供：

```

```

```
 ↓
```

# 18. Session

M6.2 只建立最小 Session Model。

例如：

```
session_id
```

允许：

```
client 提供 session_id
```

或者：

```
server 生成 session_id
```

但是：

> 不实现真正的持久化 Memory。

不要加入：

```
Redis
PostgreSQL
SQLite
Vector DB
```

Session 只作为 Contract / Application Model。

# 19. Agent Runtime 接口预留

M6.2 可以定义 Protocol：

```
class AgentRuntime(Protocol):
    def handle(self, request: ChatRequest) -> ChatResponse:
        ...
```

M6.2 使用：

```
StubAgentRuntime
```

未来：

```
M6.3
LLMAgentRuntime
```

再进一步：

```
M6.5
LangGraphAgentRuntime
```

这样：

```
ChatService
     ↓
AgentRuntime
```

不会绑定具体 Agent Framework。

# 20. 为什么现在不直接 LangGraph

这是本阶段的重要架构原则。

不要因为最终需要 Agent，就在 M6.2 直接：

```
LangGraph
↓
LLM
↓
Tool Calling
```

现在先验证：

```
Agent Backend
    ↓
Agent API
    ↓
PlatformClient
    ↓
Platform Backend
```

如果这一层没有稳定：

> 后面 LangGraph 出问题时，你无法判断是 Agent 问题还是 Platform 通信问题。

M6.2 应该建立一个干净的基线。

# 21. Tool Gateway 暂时只定义接口

可以预留：

```
agent_backend/tools/
```

但 M6.2 不需要真正实现完整 Tool Gateway。

可以只定义概念接口：

```
class AgentTool(Protocol):
    name: str

    def execute(...):
        ...
```

如果没有实际使用需求，可以连这个都推迟。

不要为了“未来扩展”制造大量空类。
