# M6.1：Platform Backend HTTP Server

## 0. 任务目标

当前项目已经完成 M0～M5，并完成 M6.0 三端架构边界与 API Contract。

M6.0 已经建立：

```
Frontend
    │
    │ Agent API Contract
    ▼
Agent Backend
    │
    │ Platform API Contract
    ▼
Platform Backend
    │
    ▼
EDA
```

M6.0 当前状态：

```
contracts/
├── platform-api.yaml
├── agent-api.yaml
└── schemas/

src/aemp/api/
├── errors.py
├── schemas.py
└── services.py
```

其中：

```
PlatformApi
```

已经作为进程内应用层存在。

# 1. M6.1 的唯一目标

把：

```
PlatformApi
```

暴露为真正的：

```
HTTP REST API
```

最终形成：

```
Agent Backend
      │
      │ HTTP
      ▼
┌──────────────────────────────┐
│      Platform Backend        │
│                              │
│ FastAPI / HTTP Server        │
│          ↓                   │
│     PlatformApi              │
│          ↓                   │
│ Flow / Run / QA / Artifact   │
│          ↓                   │
│ EDA Tools                    │
└──────────────────────────────┘
```

# 2. 核心原则

必须遵守：

> **HTTP Layer 是 Transport Adapter，不是新的业务层。**

正确：

```
HTTP Request
    ↓
FastAPI Route
    ↓
PlatformApi
    ↓
Existing Core
```

禁止：

```
HTTP Request
    ↓
FastAPI Route
    ↓
重新实现 Flow
```

也禁止：

```
FastAPI Route
    ↓
FlowEngine
```

因为 M6.0 已经定义：

```
PlatformApi
```

作为 Application Service Boundary。

# 3. 本阶段允许做什么

允许：

- FastAPI
- Uvicorn
- HTTP routing
- Request/Response DTO
- HTTP status mapping
- JSON serialization
- API error handling
- OpenAPI schema 对齐
- health endpoint
- contract tests
- HTTP integration tests
- CORS 仅在确有必要时做最小配置

# 4. 本阶段禁止做什么

严格禁止：

```
❌ Agent
❌ LangGraph
❌ LLM
❌ MCP
❌ Skill
❌ Progressive Disclosure
❌ Human Approval
❌ Interrupt / Resume
❌ RAG
❌ Diagnosis
❌ Frontend
❌ SSE
❌ WebSocket
❌ Multi-Agent
❌ Redis
❌ Celery
❌ 新数据库
❌ 修改 result_v0
❌ 修改 FlowEngine 语义
❌ 修改 QAEngine 语义
❌ 直接从 HTTP Route 调 Driver
```

注意：

虽然未来 Agent 会使用 SSE，但 **M6.1 先只实现同步 REST API**。

SSE 放到后续 Agent Backend。

# 7. FastAPI App

建立：

```
app = FastAPI(...)
```

要求：

- API title 与项目名称一致
- API version 与 Contract 对齐
- `/docs`
- `/openapi.json`
- `/healthz`

# 8. Health Endpoint

实现：

```
GET /healthz
```

响应：

```
{
  "status": "ok"
}
```

注意：

`healthz` 只表示 Platform HTTP Server 本身存活。

不要因为：

```
Docker 不可用
Yosys 不存在
OpenSTA 不存在
```

就让 `/healthz` 返回 500。

如果未来需要 EDA environment readiness：

```
GET /readyz
```

可以单独设计。

本阶段可以不实现 `/readyz`。

# 9. Run Flow Endpoint

Contract：

```
POST /api/v1/flows/run
```

FastAPI route：

```
POST /api/v1/flows/run
        ↓
Request Schema
        ↓
PlatformApi.run_flow(...)
        ↓
Existing FlowEngine
        ↓
Run
```

不要重新实现：

```
Flow validation
Flow execution
Run creation
```

# 10. Run Flow Request

严格遵守：

```
contracts/platform-api.yaml
```

例如：

```
{
  "flow": "configs/flows/rtl_to_sta.yaml",
  "inputs": {}
}
```

当前 M6.0 已明确：

> inputs override 暂不支持。

因此如果当前 PlatformApi 对 inputs override 不支持：

必须返回：

```
400 INVALID_REQUEST
```

而不是悄悄忽略。

不要：

```
用户传 inputs
     ↓
后端忽略
     ↓
仍然执行
```

这会造成 API 语义欺骗。

# 11. Run List

实现：

```
GET /api/v1/runs
```

参数：

```
limit
offset
status
```

必须复用：

```
RunIndex.query_runs(...)
```

不要：

```
SELECT *
```

然后在 Python 中分页。

M6.0 已经明确：

> 分页与 status filter 属于 SQL 层。

# 12. Run Detail

实现：

```
GET /api/v1/runs/{run_id}
```

执行：

```
run_id validation
        ↓
Run lookup
        ↓
PlatformApi
        ↓
DTO
```

必须在访问 filesystem / SQLite 之前进行：

```
run_id format validation
```

不能允许：

```
../../
```

等路径穿越。

如果不存在：

```
{
  "error": {
    "code": "RUN_NOT_FOUND",
    "message": "...",
    "details": {}
  }
}
```

HTTP：

```
404
```

# 13. QA Endpoint

实现：

```
POST /api/v1/runs/{run_id}/qa
```

请求：

```
{
  "rule_pack": "configs/rules/base_timing.yaml"
}
```

调用：

```
PlatformApi
    ↓
QAService
    ↓
QAEngine
```

不能在 HTTP 层重新执行：

```
if wns < 0:
    ...
```

QA 规则仍然只存在：

```
RulePack
QAEngine
```

# 14. Artifact List

实现：

```
GET /api/v1/runs/{run_id}/artifacts
```

只返回 Run 已注册 Artifact。

例如：

```
{
  "run_id": "...",
  "artifacts": [
    {
      "artifact_id": "...",
      "role": "timing_report",
      "path": "artifacts/timing.rpt",
      "bytes": 1234,
      "sha256": "..."
    }
  ]
}
```

不要扫描：

```
runs/{run_id}/
```

然后把所有文件都当 Artifact。

Artifact 必须来自：

```
Run Artifact Registry
```

# 15. Artifact Detail

实现：

```
GET /api/v1/runs/{run_id}/artifacts/{artifact_id}
```

M6.1：

> **只返回 Artifact 元数据。**

不要返回：

```
文件内容
```

不要实现：

```
arbitrary file read
```

未来如果需要：

```
get_artifact_content
```

应该作为单独能力设计，并加入：

```
size limit
content type
allowlist
path boundary
approval / policy
```

# 16. Error Handling

统一处理：

```
ApiError
```

映射：

```
ApiError
    ↓
HTTP status
    ↓
error_document()
```

保持 M6.0 定义：

```
INVALID_REQUEST
RUN_NOT_FOUND
FLOW_NOT_FOUND
FLOW_VALIDATION_FAILED
TOOL_EXECUTION_FAILED
TOOL_ENVIRONMENT_UNAVAILABLE
QA_EVALUATION_FAILED
ARTIFACT_NOT_FOUND
INTERNAL_ERROR
```

不要把 Python traceback 返回给客户端。

开发日志中可以记录 traceback。

HTTP Response 中不能出现：

```
stack trace
local filesystem
environment secret
Docker command
```

# 17. 500 Internal Error

所有未预期异常：

```
Exception
```

必须：

1. server-side logging
2. 返回稳定：

```
{
  "error": {
    "code": "INTERNAL_ERROR",
    "message": "Internal server error",
    "details": {}
  }
}
```

不要把：

```
str(exception)
```

直接作为 production API message。

# 18. Request Validation

FastAPI/Pydantic 可以负责 HTTP DTO validation。

但是：

> **业务 validation 仍然属于 PlatformApi / Core。**

例如：

```
HTTP Schema
    ↓
类型正确
    ↓
PlatformApi
    ↓
业务合法
```

不能因为 Pydantic 接受了：

```
{
  "flow": "../../foo"
}
```

就认为它合法。

# 19. Contract 必须保持一致

这是本阶段最重要的验收标准。

以下三者必须一致：

```
contracts/platform-api.yaml
        ↕
FastAPI implementation
        ↕
tests
```

如果 FastAPI OpenAPI 自动生成结果与：

```
contracts/platform-api.yaml
```

有差异：

必须修正。

不要简单地把：

```
contracts/platform-api.yaml
```

重新生成覆盖掉。

因为：

> Contract 是设计源，而不是实现副产品。

# 20. API Version

保持：

```
/api/v1/
```

不要出现：

```
/api/
```

或者：

```
/api/v2/
```

当前不做 v2。

# 21. CORS

M6.1 可以提供配置：

```
AEMP_CORS_ORIGINS
```

默认：

```
disabled / empty
```

不要：

```
allow_origins=["*"]
```

作为默认生产配置。

因为未来 Frontend 与 Agent Backend 会独立部署。

CORS 最终应该属于：

```
Frontend ↔ Agent Backend
```

而 Platform Backend 未来主要被 Agent Backend 调用。

因此 M6.1 不需要为了未来 Frontend 预先放开所有 Origin。

# 22. 配置

Server 配置尽量通过环境变量：

```
AEMP_HOST=127.0.0.1
AEMP_PORT=8000
AEMP_LOG_LEVEL=INFO
```

不要硬编码：

```
uvicorn.run(app, host="0.0.0.0", port=8000)
```

可以提供默认值，但必须允许覆盖。

# 23. 启动方式

建议支持：

```
uvicorn aemp.api.http:app
```

或者：

```
python -m aemp.api.http
```

如果项目已有 CLI，可以增加：

```
aemp serve
```

但是：

> 不要破坏现有 `aemp` CLI。

如果增加：

```
aemp serve
```

必须是增量功能。

# 24. 日志

HTTP Server 应记录：

```
request_id
method
path
status
duration_ms
```

不要记录：

```
API key
Authorization
完整敏感输入
```

建议：

```
X-Request-ID
```

如果客户端没有提供，可以服务端生成。

但不要为了这一阶段引入复杂 tracing 系统。

LangSmith 后面处理 Agent Trace。

# 25. Timeout

M6.1 不要在 HTTP Server 自己实现 EDA timeout。

已有：

```
ToolDriver
DockerToolExecutor
FlowEngine
```

已经负责：

```
EDA execution timeout
```

HTTP 层只需要考虑：

> 长时间 Flow 请求可能导致 HTTP connection 长时间占用。

因此文档中明确：

```
M6.1 = synchronous execution
```

未来：

```
Agent / async job / SSE
```

再解决长任务问题。

不要现在引入 Celery / Redis。

# 27. Integration Test 不要强依赖 Docker

测试分成：

```
Unit
    ↓
HTTP validation / error / routing

Integration
    ↓
temporary run / fixture

EDA E2E
    ↓
Docker
```

如果本机没有 Docker：

```
EDA E2E = skipped
```

不能因此让整个测试失败。
